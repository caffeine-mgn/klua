## 🔴 Критическое (воспроизведено): #1, #2

### #1. JVM: коллизия ID → closure вызывает ЧУЖУЮ Kotlin-лямбду

**Где:** `src/jvmSharedMain/kotlin/pw/binom/lua/ObjectContainer.kt:90-91`,
`src/jvmSharedMain/kotlin/pw/binom/lua/LuaNative.kt:13,142`

**Суть:** два НЕЗАВИСИМЫХ счётчика пишут в одну и ту же карту `LuaNative.callbacks`:

- `ObjectContainer.nextClosureId()` — статический counter стартует с `1` (`ObjectContainer.kt:90`);
- `LuaNative.nextCallbackId()` — статический counter тоже стартует с `1` (`LuaNative.kt:13`).

Оба идут через `LuaNative.setCallback(id, bridge)`. Диапазоны ID пересекаются
(конструктор `LuaEngine` ещё и «съедает» один `nextCallbackId` на `closureAutoGcFunction`),
поэтому `makeClosure` и `createACClosure` перезаписывают bridge друг друга. Этот же путь
используется в `__gc`. Итог: Lua-функция может вызвать совсем не ту Kotlin-лямбду.

Это `I11` из старого ревью — но там он помечен как «housekeeping/info». На деле это
порча диспетчеризации вызовов.

**Repro (JVM, 200 closure + 200 AC-closure):**
```
closure c1 dispatched to 'a0'
closure c2 dispatched to 'a1'
...
total mismatched closures: 199
```

**Фикс:** единый аллокатор ID в `LuaNative`; `ObjectContainer` должен брать id оттуда
(свой counter удалить). Добавить регрессионный тест: создавать `makeClosure` и
`createACClosure` из одного движка «вперемешку» и проверять, что каждый вызывает свою лямбду.

### #2. JVM: `UserData.dispose()` делает двойной `luaL_unref` → порча freelist реестра Lua

**Где:** `src/jvmSharedMain/kotlin/pw/binom/lua/LuaValue.kt:62-73` (`UserData.dispose`),
`src/jvmSharedMain/kotlin/pw/binom/lua/LuaValue.kt:333-341` (`RefAction`),
`src/jvmSharedMain/kotlin/pw/binom/lua/RefCleaner.kt:92-97` (`RefCleanable.clean`)

**Суть:**
```kotlin
fun dispose() {
    val p = ptr ?: return
    cleanable.clean()      // RefCleanable.clean() НЕ отменяет действие, а ВЫПОЛНЯЕТ его
    StaticRefs.dispose(p)
    if (ll.state != 0L) LuaNative.unref(ll.state, LUA_REGISTRYINDEX, refId)  // прямой unref
}
```
`RefCleanable.clean()` вызывает `action.run()` → `RefAction` → `ll.deferUnref(refId)`, и
**плюс** здесь же идёт прямой `LuaNative.unref` того же слота. Слот анрефается дважды.
Комментарий в коде («Cancel the registered Cleaner…») описывает задуманное поведение,
которого фактически нет.

Lua `luaL_unref` не идемпотентен: второй `unref` того же слота зацикливает freelist
(`t[ref] = ref`), после чего `luaL_ref` начинает возвращать один и тот же слот на все
запросы → `TableRef`/`FunctionRef`/`UserData` молча указывают на один и тот же Lua-объект.

**Repro (JVM):**
```
refIds after dispose: 5, 5     // две разные функции получили один и тот же registry-слот
```
(тест: `engine.createAC(...).dispose()`, затем два `engine.eval("return function() end")`
и сравнение `refId`.)

**Фикс:** либо сделать так, чтобы `dispose()` не вызывал выполняющий action
(нужен «отменяющий» API), либо отдать весь `unref` cleaner-пути и убрать прямой вызов.
Регрессионный тест: после `dispose()` два последовательных `makeRef` должны давать разные `refId`.

## 🟠 Латентное (не воспроизводится)

### #3. POSIX: `ObjectContainer.removeClosure(FunctionValue)` — двойной dispose StableRef

**Статус:** НЕ воспроизводится как сбой — `StableRef.dispose()` в K/N идемпотентен
(`removeClosure -> true`, повторный `dispose()` не бросает). Понижено из 🔴 в латентное:
это логическая ошибка владения, но наблюдаемого отказа сейчас нет.

**Где:** `src/posixMain/kotlin/pw/binom/lua/ObjectContainer.kt:73-88` (и `:61-71` для `FunctionRef`)

**Суть:**
```kotlin
val removed = remove(underlying)   // remove(Any) уже делает ptr.asStableRef<Any>().dispose()
lud.dispose()                      // ...а это dispose()'ит ТОТ ЖЕ StableRef ещё раз
```
`add(data)` кладёт `dataStableRef.asCPointer()` и в upvalue (через `LightUserData`), и в
обе карты; `remove(underlying)` по identity находит этот указатель и освобождает StableRef,
после чего `lud.dispose()` освобождает его повторно.

На практике не падает (`removeClosure -> true`) — K/N, похоже, терпит повторный `dispose()`,
— но это логическое двойное освобождение и хрупко. Путь `removeClosure(FunctionRef)`
делегирует сюда же. Покрытия тестами нет вовсе.

**Фикс:** убрать `lud.dispose()` (освобождение уже сделано `remove`), либо сделать
владение StableRef одноуровневым. Добавить тест на `removeClosure` для POSIX.

## 🟡 Среднее

### #4. JVM `FunctionRef.toValue()` всегда возвращает `FunctionValue(0)`
`src/jvmSharedMain/kotlin/pw/binom/lua/LuaContext.kt:214` — при `ref=false` для функции
хардкодится `LuaValue.FunctionValue(0)`, `callbackId` теряется. Следствия:
- `ObjectContainer.removeClosure(FunctionRef)` жёстко возвращает `false`
  (`src/jvmSharedMain/kotlin/pw/binom/lua/ObjectContainer.kt:65`) → bridge не снимается
  (это старый открытый W2);
- `pushValue(FunctionValue(0))` пушит cclosure с несуществующим id → `invokeCallback`
  тихо возвращает 0 (no-op).

### #5. JNI-строки некорректны для настоящего UTF-8
`src/jvmMain/c/klua_jni.c` — `str_from_lua`/`NewStringUTF` и `pushString`/`GetStringUTFChars`
работают с *modified* UTF-8. Lua-строки — произвольные байты: 4-байтные кодпоинты (эмодзи)
и `\0` внутри строки дают порчу/обрезку. `loadString` (`GetStringUTFLength` +
`luaL_loadbufferx`) тоже несовместим с сырыми байтами.

### #6. `LuaNative.lastError` — статическое разделяемое поле
`src/jvmSharedMain/kotlin/pw/binom/lua/LuaNative.kt:179,210,213`. Общее для всех движков и
потоков: при параллельных callback'ах сообщение об ошибке может принадлежать чужому исключению.

### #7. `cancel()` противоречив
`src/commonMain/kotlin/pw/binom/lua/LuaEngine.kt` (Kdoc) обещает отмену «следующего
eval/call, если ничего не выполняется», но `prepareLimits()` в начале операции вызывает
`resetLimits()`, который стирает флаг `cancel`. То есть отменить «следующий» вызов нельзя —
только текущий.

### #8. Асимметрия `FunctionValue` JVM vs POSIX
JVM: `FunctionValue(callbackId: Int)` без upvalues. POSIX: `FunctionValue(ptr, upValues)`.
JNI `pushCClosure` вообще игнорирует параметр `n` (upvalues) — `klua_jni.c`. Общий
`expect`-контракт, разная семантика.

### #9. Расхождение семантики числовых ключей
`LuaValue.Number(5.0) != LuaValue.LuaInt(5)` (разные `equals`), тогда как в Lua `t[5]`
и `t[5.0]` — один ключ. Поиск по `TableValue` из Kotlin может не найти ключ, который Lua бы нашёл.

## Приложение: воспроизведение #1 и #2 (JVM)

До фикса воспроизводилось так (факты: 198/200 чужих вызовов и `refId 5 == 5`):

```kotlin
class TempReproTest {
    @Test
    fun closureIdsCollideWithCallbackIds() {
        val engine = LuaEngine().apply { openStandardLibs() }
        val oc = ObjectContainer()
        val closures = (0 until 200).map { i -> oc.makeClosure { listOf("c$i".lua) } }
        val acs = (0 until 200).map { i -> engine.createACClosure { listOf("a$i".lua) } }
        closures.forEachIndexed { i, c -> engine["c$i"] = c }
        acs.forEachIndexed { i, a -> engine["a$i"] = a }
        var mismatches = 0
        for (i in 0 until 200) {
            val got = engine.eval("return c$i()")[0].checkedString()
            if (got != "c$i") mismatches++
        }
        assertEquals(0, mismatches)   // факт до фикса: 198/200
    }

    @Test
    fun userDataDisposeDoesNotDoubleUnrefRegistry() {
        val engine = LuaEngine().apply { openStandardLibs() }
        engine.createAC("payload").dispose()
        val r1 = engine.eval("return function() end")[0] as LuaValue.FunctionRef
        val r2 = engine.eval("return function() end")[0] as LuaValue.FunctionRef
        assertNotEquals(r1.refId, r2.refId)   // факт до фикса: 5 == 5
    }
}
```

`src/jvmTest/kotlin/pw/binom/lua/JvmRegressionTest.kt` (те же ассерты, 100+100
вместо 200+200) и проходят после фиксов.
